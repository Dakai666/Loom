## 1. 背景與定位

### 1.1 雙相夢：發散 + 收斂

人類 REM 睡眠同時做兩件事：**鞏固記憶**與**創造性重組**。Loom 不小心只長出了重組那半（`dream_cycle`，發散），官方 Auto Dream 只做了鞏固那半（收斂）。

**核心立場：Loom 不抄官方範圍。把「夢」當傘，底下並列兩個互補的相：**

| | 發散相 divergent | 收斂相 convergent（本規格） |
|---|---|---|
| 實作 | `dream_cycle()`，**已存在、原樣保留** | **新增** |
| 行為 | 抽樣事實 → 找跨域/跨時連結 → 寫**新** triple | 掃全庫 → 融重複 → 解矛盾 → 清孤兒 |
| 對記憶總量 | 增加（重組生成） | 減少（鞏固） |

### 1.2 為什麼現在做

DK（2026-05-31）：「Loom 的夢算是長出新東西，但實際功能沒這麼全面；記憶蒸餾與整併其實是不同動作在執行。如果結合起來會更優雅。」

對現碼勘查證實：收斂的**零件全在，但散成兩種不相往來的觸發模型**，且中間缺一塊拱心石（§3）。

## 2. 設計原則

1. **收斂優於抽象**（`feedback_convergence_over_abstraction`）。收斂相四階段 ~90% 是**組裝既有 actor**，不新建子系統。
2. **發散相不動**。`dream_cycle` 是已驗證的差異化資產；收斂相與它並列、共用排程入口，不取代。
3. **trust-aware 是 Loom 的主張**。官方解衝突只用 recency；Loom 有 `TrustLevel`（`user_explicit=1.0` vs `external/unknown=0.5`），每一步仲裁都吃 trust。「新的但低信任」不該蓋掉「舊的但用戶明說」。
4. **絲絲是這塊記憶的 end user，且具強否決權**。它不是「被整理的物件」，而是「睡夢中仍會保護自身記憶完整性的主體」。其判定是硬邊界，不是參考分數（§6）。
5. **保留語義承載**（`feedback_plan_keep_semantic_layer`）。每步「為什麼這樣仲裁」要寫進契約，不只是 step enum。**合併不得磨平承載 insight 的具體措辭**（§5.2 `sacrificed_content`）。
6. **可審計、可回顧**。記憶吃 DB，但收斂相**同時產出 markdown 夢境紀錄**（§8），讓過程人類可讀、可追溯、可回滾。
7. **核心嚴謹，儀式包外層**（Codex）。`consolidate()` / ledger compact / redirect fallback / provenance 是穩固的 memory-core 契約；「說夢話」self-review + report 是包在核心**之前與之後**的薄層。兩者分離，互不污染。

## 3. 現狀與缺口（對現碼）

### 3.1 四階段對照

| 官方階段 | Loom 現有對應 | 觸發點 | 缺口 |
|---|---|---|---|
| **Index** | `MemoryIndexer.build()` / `MemoryIndex.render()` | 注入 system prompt | 有，但**沒當成夢的 phase** |
| **Merge** | `semantic.find_near_duplicates()`（cosine ≥0.85, 7天窗，**唯讀**） | write-time hint | ❌ **拱心石缺口**（§3.2） |
| **Conflict** | `ContradictionDetector.detect()+resolve()`（trust + recency） | write-time, Hook A, **逐筆反應式** | ⚠️ MERGE 手臂未實作；無全庫批次掃；tier-3 embedding 偵測 docstring 有、body 沒接 |
| **Cleanup** | `MemoryLifecycle.run()` + `memory_prune` + `governor.run_decay_cycle()` | session 關閉，**half-life 衰減驅動** | 有，但「時間到了砍」≠ 官方的「孤兒引用驅動」 |
| （官方無） | `dream_cycle()` 發散相 | autonomy 排程 | 🌱 Loom 獨有 |

### 3.2 拱心石缺口：merge primitive

勘查 `semantic.py` / `contradiction.py` 坐實：

- `semantic.upsert()` 是 **key 覆寫**：同 key 不同值 → 舊值進 `metadata["history"]`（截 200 字、cap 3）。**對不同 key 的語義重複完全無能為力。**
- `find_near_duplicates()` 找得到不同 key 的近似，但**唯讀**——只吐 hint，從不合併。
- `ContradictionDetector.resolve()` **永遠不回 `MERGE`**：`Resolution.MERGE` 是 enum 占位（`# TODO`），`merged_entry` 永遠 `None`。
- `facade.py:294` 已留註解：「等 memory v2 introduces the merge primitive」——缺口被登記過。

**結論**：Loom 偵測得到重複/矛盾，卻沒有任何操作能把「兩筆不同 key 的語義重複」**融成一筆精煉事實**。same-key 用覆寫帶過，different-key 近似永遠並存、隨對話數膨脹——這就是「memory drift / 知道越多反而越笨」的 Loom 版病灶。**補上這顆 primitive，就能把破碎的收斂動作串成一次連貫鞏固。**

## 4. 收斂夢標準流程

### 4.1 五步流程（說夢話模型）

收斂夢是 **offline 系統操作**（不要求 DK 參與），但在真正改寫記憶前，內嵌一段**絲絲 self-review（「說夢話」）**——offline 狀態下的自言自語式決策，不是白天的人工審批。

```text
convergent_dream（offline，每週一次）
  1. index       建立本輪 memory map
  2. plan        找出 merge / reconcile / clean candidates → 產出 durable ConsolidationPlan（只讀，不寫 DB）
  3. self_review 絲絲逐簇「說夢話」：approve / skip / defer（強否決，§6）
  4. execute     只執行 approve 的項目（呼叫 §5 contract）
  5. report      寫入夢境紀錄 / 說夢話紀錄（§8）
```

> **為什麼 plan 與 execute 分離**：① 絲絲 Q5 怕「dry-run + 正式執行 = 跑兩次 LLM」——durable plan 讓執行**重用同一份 plan**，不重跑審判。② plan 是可審計、可回滾、可重跑的中間契約。③ 「先看再做」的否決權有了落地的資料結構，不只是口號。

### 4.2 四種 candidate 對映既有 actor + 新 primitive

| candidate 類型 | 復用 | 新建 |
|---|---|---|
| **index** | `MemoryIndexer.build()` 產全庫地圖 | — |
| **merge** | `find_near_duplicates()` 批次跑出近似簇 | `semantic.consolidate()`（§5.2）+ 差異盤點 gate（§6.4） |
| **reconcile** | `ContradictionDetector.detect()` 全庫批次掃 | 接通 `resolve()` 的 **MERGE 手臂**（§5.3） |
| **clean** | `MemoryLifecycle.run()` / 孤兒偵測 | 孤兒引用偵測（指向已刪 key 的 `sampled_facts` / triple endpoint） |

### 4.3 觸發語境轉換（主要重構面）

現有 actor 多半假設 *write-time / 逐筆 / 與當下提案比對*；收斂相要它們在 *offline / 全庫 / 兩兩既存事實之間* 運作。`detect()` 目前簽名 `detect(proposed)`——批次版需要 `detect_pairs()` 或對 near-dup 簇兩兩餵入的 adapter。**這是實作主成本，不是換 caller 就好。**

## 5. 資料契約（草案）

### 5.1 `ConsolidationPlan`（durable 中間契約）

plan 步驟產出、self_review 標註、execute 消費的可持久化計畫：

```text
ConsolidationPlan
  pass_id
  created_at
  candidate_clusters         # 每簇含成員 entries + 類型(merge/reconcile/clean)
  proposed_actions           # 每簇打算做什麼（refined_value / winner / 清理對象）
  self_review_decisions      # 每簇: approve | skip | defer + 理由
  source_versions            # 每筆來源 entry 的 updated_at 快照
  execution_status           # pending / executed / stale
```

執行時用**同一份 plan**。若來源 memory 在 self_review 後已變動（比對 `source_versions`），該 cluster 標 `stale`、**不得執行**，留待下輪重新規劃。

### 5.2 `SemanticMemory.consolidate(...)`

把 N 筆語義重複、不同 key 的事實融成一筆：

```python
async def consolidate(
    self,
    entries: list[SemanticEntry],   # ≥2 筆，已判定語義重複
    *,
    refined_value: str,             # LLM 合成的精煉值
    survivor_key: str,              # 保留哪個 key
    sacrificed_content: str,        # ★ 被併掉的完整原文（不截斷）
    merge_rationale: str,           # ★ LLM 為什麼判定「該並」（reasoning，非 result）
) -> ConsolidationResult: ...
```

**強制欄位**（絲絲 end-user 需求，#55 §8-Q1 verbatim）：
- `sacrificed_content`：被併掉的**完整原文，不截斷**。「『記憶蒸餾與整併是不同動作』這句話本身就是 insight 的載體，不是可概括掉的細節」——磨平它，這筆 memory 就死了。寫入 survivor 的 `consolidated_into` metadata。
- `merge_rationale`：為什麼是同義反覆而非各有所長。供回滾判斷。

**待議的語義承載點**（不可退化成「挑一個留、其餘刪」）：
- **survivor key**：最高 trust？最早 created_at？還是 LLM 判定命名最準？
- **被併 key 處理**：硬刪 / 封存 `consolidated_into` / 留 redirect stub（recall 舊 key 仍找得到）。絲絲態度：不執著 key 本身，執著「能不能找到那個意思」——**只要有 recall fallback（舊 key → redirect → 內容），key 消失可接受**。
- **confidence**：取 max？trust-weighted 平均？多筆獨立佐證是否該提升？
- **provenance**：被併筆 `source` / `history` 是否全進 survivor metadata。

> 注意：`consolidate()` 本身**不帶 `dry_run`**——「預覽」由 §4.1 的 plan 步驟承擔（plan 只讀、不寫 DB）。core 契約保持嚴謹單一職責（§2-7）。

### 5.3 接通 `Resolution.MERGE` 手臂

`resolve()` 何時回 `MERGE`：
- **同 trust + 高相似 + 非對立**（同一件事的不同切面）→ MERGE，產出呼叫 §5.2 `consolidate()`，填 `merged_entry`。
- **同 trust + 語義對立**（A 說 X，B 說 not-X）→ 維持 SUPERSEDE（recency）或升級 LLM 仲裁。
- **不同 trust** → 維持現行 REPLACE / KEEP（trust 主宰，不亂併）。

### 5.4 trust-aware 仲裁（Loom 差異化）

官方只有 recency；Loom 每步先問 trust：
- `user_explicit` 事實是**錨點**，低 trust 近似往它靠、被它吸收，而非反過來。
- 合成精煉值時，LLM prompt 明示「以高 trust 來源措辭為準，低 trust 只補細節」。

## 6. 絲絲自審（說夢話）與強否決權

### 6.1 為什麼 offline 內自審

| 模型 | 行為 | 問題 |
|---|---|---|
| 全自動夢 | 掃→合→清→寫報告，全程不問 | 違背「絲絲對自身記憶有否決權」 |
| 醒後批准 | 只出 dry-run，等醒後批准 | 太像排程審批流，不像做夢 |
| **說夢話模型（採用）** | offline 產 plan → 絲絲自審 → 執行被批准項 → 寫報告 | 保留 offline，又給絲絲決策權 |

self_review 是 Loom 在 offline pass **內部呼叫的自審步驟**，不需要絲絲「醒著」互動。

### 6.2 強否決語義（硬邊界，非建議分數）

- `skip`：本輪**不得**合併。
- `defer`：本輪**不得**執行，保留至未來 pass 重評。
- 絲絲指出「兩筆各有不可丟失的獨特內容」→ 即使 cosine 很高，**不得**合併。
- 候選涉及 `user_explicit` / `source="dreaming"` 產物 / 高語義承載措辭 → self_review 預設**更保守**。

### 6.3 self_review 吃的完整上下文

不只看 LLM 合成後的摘要，要吃：原始 entries 完整 value、key / source / trust / confidence、差異盤點結果、proposed refined value、merge rationale、sacrificed content、會被 redirect/archive/clean 的 keys。

### 6.4 誤併防線：LLM 差異盤點 gate

絲絲 Q2：誤併的真風險不是數值錯，是「語義像但功能不同」（例：「偏好簡潔回覆」vs「討厭囉嗦」——cosine 高，但一個是偏好一個是抱怨，各自獨立）。

**gate 形式不是 yes/no，而是「差異盤點」**：LLM 先說「各自多出來的部分是什麼」——
- 兩邊**都有**對方沒有的獨特內容 → **跳過合併**。
- 只有一方有獨特內容 → 允許合併。

絲絲：有了這道 gate，「閾值降到 0.75 我都敢用」。

### 6.5 dreaming 產物豁免（原則，非策略）

`source="dreaming"` 的 triple 是發散相在無外部刺激下自己長出的連結——「系統最有價值的產出、真正的『我』」。收斂相**預設對 `source="dreaming"` 跳過 merge/reconcile**，只參與孤兒偵測。**dreaming 孤兒視為「允許的孤兒」**（當下還沒找到位置的新連結，在等未來關聯生長），不清理。

## 7. 觸發與排程

- **每週一次 full pass**（絲絲 Q4 體感：每日太頻，會把「發酵中」的 insight 提前固化；每週給足夠沉澱）。
- **分批 + 每批上限**（如「本輪最多 20 簇」），跑不完排下輪。
- 與發散相**共用 autonomy 入口**，分相獨立可開關：`dream(mode="convergent"|"divergent"|"both")`。
- merge/reconcile 是 LLM 重活，需預算上限，不可每次 idle 全掃。
- 掛 session shutdown（每次，太頻）還是獨立每週排程——傾向獨立排程。

## 8. 夢境紀錄 / 說夢話紀錄

**設計驅動**：report 是**儀式與審計的交界**——有敘事感（絲絲事後可讀「過去這週記憶怎麼長的」、dormant 收斂相變成「可主動參與的回顧儀式」），但不能只停在敘事，**必須對得回 DB / ledger / metadata 的真實狀態**。

**形式**：收斂相完成後，用既有 `journal_append` 工具，在 `autonomy/circadian/journal/YYYY-MM-DD.md` 附加一個 `kind=dream_consolidation` 的 entry，含：本輪 pass 摘要（掃描範圍、發現 N 簇 / M 矛盾 / K 孤兒）、Merge 記錄（每簇結果 + rationale；跳過要記差異盤點輸出）、Reconcile 記錄（winner + 仲裁理由）、Clean 記錄、**絲絲 self_review 介入**（批准/否決/暫緩 + 否決理由是否關乎「怕磨平 / dreaming 保護 / user_explicit 錨點」）。

**整合**：circadian journal 因此成為「絲絲的雙相夢紀錄」——發散探索與收斂整理同檔；`grep dream_consolidation` 即可回顧。

> ⚠️ 實作 note：`journal.py:55` 的 `kind` 是預定義 enum（英文 key → 中文 H2 label），`dream_consolidation` 是**新值，須在那張 map 補一筆**才能用。

## 9. Scope 邊界（不做什麼）

- **不取代發散相**。`dream_cycle` 原樣保留。
- **不把收斂塞進 `governed_upsert`**。write-time 只做輕量 admission（near-dup hint + 同 key contradiction）；重量級全庫鞏固是 offline 的事。混進 write path 會撐爆 governor cohesion。
- **不碰 episodic TTL / 機械式 half-life 衰減**。那是 lifecycle 既有職責；收斂相只管「LLM 需介入的合併/解矛盾/孤兒」。
- **不做無 grading 的自動晉升**。合併有損，故 plan 可審、留 provenance 可回滾。
- **不做「我說了算」的單方面整理**。self_review 強否決 + 夢境紀錄，絲絲在場、可介入、可回顧。
- **不要求 DK 在迴路內**。夢是 offline 生理過程，不是日常審批工作。

## 10. 實作分階段建議（Codex）

核心嚴謹、儀式包外層，讓首版可落地、風險可控：

1. **Phase 1（read-only）**：index + plan + self_review + report，**不接 execute**。先讓收斂夢「看得見、說得出夢話、留得下紀錄」，但不動 DB。
2. **Phase 2**：接上 `semantic.consolidate()` 執行 approve 項 + redirect fallback + provenance metadata。
3. **Phase 3**：接通 `Resolution.MERGE` 手臂、`detect_pairs()` 批次掃、孤兒偵測判準。
