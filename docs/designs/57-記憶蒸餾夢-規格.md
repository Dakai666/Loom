# 記憶蒸餾夢 — 實作規格

> 狀態：定案 r2（2026-10-19，納入 Loom Agent review；DK 拍板大夢時程 B）
> 關聯：#613（方向 E）、`56-記憶鞏固夢-收斂相規格.md`（收斂夢，本規格重用其管線）
> 前置已合併：#615（收斂夢上限可調）、#616（夢走 admission gate + 21 天半衰期）、#617、#618（census 分群）

---

## 1. 為什麼要改夢

DK 對夢的期待（2026-10-19）：**跨記憶的整合、蒸餾與精煉，比蹦出新聯想更重要。**

現況剛好反過來：

| 事實（2026-10-19，主 agent） | 數字 |
|---|---|
| 近 28 天新寫入中，夢產生的占比 | 532 / 878（61%） |
| 夢三元組被 recall 過的比例 | 15% |
| 夢三元組的 key 不重複率 | 2,745 個主詞 / 2,777 筆 |
| 最常見的謂詞 | `contrasts_with` / `enables` / `parallels` / `mirrors` |

12 小時一次的主題夢做的是「隨機抽樣 → 找出類比 → 寫入新的三元組」，淨效果是**增加**記憶。我們要的是淨效果**減少**、同時讓剩下的記憶更好用的夢。

兩個 agent（主 agent、`ruby_xin`）都抱怨過記憶重複，這是共同的需求。

## 2. 定位：三種夢

| 夢 | 頻率 | 做什麼 | 淨效果 |
|---|---|---|---|
| **自由夢**（03:00，保留） | 每天 1 次 | 跨領域聯想，產生三元組假說 | +（受 admission gate 與 21 天半衰期約束，#616） |
| **蒸餾夢**（新，取代 12 小時主題夢） | 每天 2 次 | 挑一個主題鄰域，精煉成一條，**取代**原來的多條 | − |
| **收斂夢**（每週，既有） | 每週 1 次 | 合併近似重複、處理矛盾、清孤兒 stub | − |

蒸餾夢跟收斂夢是互補的：收斂夢處理「同一件事寫了很多遍」（cos ≥ 0.85），蒸餾夢處理「同一個主題散成很多條」（0.70–0.85）。

## 3. 相似度區間（實測校準，2026-10-19）

用 live DB 抽樣（`qwen3-embedding:0.6b`）：

| 區間 | 實際長相 | 例子 |
|---|---|---|
| ≥ 0.85 | 近似重複 → 收斂夢 | — |
| 0.78–0.85 | **同一件事換個說法**（目前會穿過 admission gate） | 「每日肖像用固定參照圖作 sub」的三種寫法 |
| 0.70–0.78 | **同主題、不同面向** | 肖像的參照圖 / 檔名格式 / 輸出目錄 |
| < 0.70 | 不同主題 | — |

→ 蒸餾鄰域 = 種子 + cos ∈ **[0.70, 0.85)** 的鄰居（≥ 0.85 的也一併納入，避免收斂夢還沒輪到）。區間要寫成設定值，不寫死在程式裡。

**定期重新校準**：蒸餾夢本身會改變 DB 的分布，所以校準不是一次性的前提。每 4 週重跑一次上表的抽樣（同樣的方法、同樣的區間），把結果附在當週的 dreams 報告裡；區間如果明顯漂移，就調整設定值。換 embedding 模型時立即重新校準。

## 4. 一場蒸餾夢的流程

沿用收斂夢的五步驟，只換掉「找候選」和「合成」：

1. **挑種子**：沿用主題夢的領域輪替（`next_themed_domain`）。在該領域裡挑**還沒被蒸餾過**、而且鄰居最多的**非夢機器產出記憶**（session / agent 等）當種子。夢三元組不當種子：它們有 21 天半衰期（#616），沒被用到就會自己離開；全是夢的鄰域也找不到合法的 survivor（§5）。
2. **收鄰域**：`find_near_duplicates(seed, min_similarity=0.70, within_days=None, limit=12)`，排除 stub。鄰域少於 3 條 → 跳過，換下一個種子。
3. **蒸餾**（LLM）：輸入鄰域全文，輸出：
   - `distilled`：一條精煉後的記憶，要涵蓋 `covers` 來源中**仍然有效**的所有主張，但**不重述鄰域中手寫記憶已經說過的主張**（見 §5 第 1 條）；
   - `covers`：被它取代的來源 key 清單（可以只是鄰域的子集，不相干的留著不動）；
   - `dropped`：判定過時或瑣碎、刻意不保留的內容，以及理由；已經由手寫記憶承載的主張也列在這裡，並註明那條手寫記憶的 key。
4. **把關**：
   - 差異盤點（`diff_inventory`，既有）：`covers` 裡每條來源的獨特資訊，要嘛出現在 `distilled`，要嘛列在 `dropped`。兩邊都沒有 → 擋下。
   - 絲絲自審（`self_review`，既有）：硬否決權不變。
5. **執行**：`semantic.consolidate(covers, refined_value=distilled, survivor_key=<covers 中信任層級最高的；同層級優先非 `rel:` key，再取最早>)`。`rel:{S}::{P}` 的 key 由三元組推導，之後同主詞同謂詞的三元組會寫到同一個 key，所以盡量不讓它當 survivor。原文全部逐字保存在 survivor 的 `metadata.consolidated_into`（含 survivor 自己的原值；survivor 若之前合併過，舊紀錄移到 `consolidation_history`；被取代的成員若之前當過 survivor，它的紀錄跟著帶過來），被取代的 key 留重導向 stub（既有語義，可回溯）。survivor 另外標上 `metadata.produced_by = "distill_dream"` 和 `metadata.distilled_at`：前者讓 §7 能查詢蒸餾產物（`source` 維持原值，不改既有語義），後者避免短時間內被重複蒸餾。這兩個欄位在 P1 就固定下來，避免 P2 之後再回頭改寫已產生的資料。

每場預設處理 5 個鄰域（`max_neighborhoods`）。成本大約是每個鄰域 3 次 LLM 呼叫，每天約 30 次。

## 5. 硬邊界（不可協商）

- **手寫記憶不刪、不覆、不複製**：`user_explicit` / `agent_memorize` 層級，以及 `milestone` temporal 的記憶，可以當蒸餾的**輸入脈絡**，但不能出現在 `covers` 裡；它們的主張也不能被改寫進 `distilled`（否則手寫原文和蒸餾改寫版會並存，製造新的重複）。手寫記憶永遠是權威副本。差異盤點同時檢查這一點：`distilled` 裡的主張如果能在鄰域的手寫記憶找到對應 → 擋下。
- **夢的三元組不當 survivor**：`source=dreaming` 的記憶可以被蒸餾掉，但 survivor 必須是非夢來源（否則精煉結果會繼承 21 天半衰期）。
- **執行前備份**：沿用收斂夢的 `snapshot_before_write`；備份失敗 → 本場降級成唯讀，報告中寫明原因（#615）。
- **stale 防護**：計畫和執行之間任何一條來源變動過 → 跳過該鄰域（重用 `execute_plan` 的 stale check）。
- **不碰 key / embedding 規則**：survivor 合併後重新 embed（既有），stub 的 embedding 保持 NULL（#617）。

## 6. 大夢（一次性全庫整理）

DK 希望這次做完後，讓 Loom Agent 做一場大夢，把過去的記憶全部好好整理、蒸餾一次。

**時程（DK 拍板 2026-10-19：B）**：蒸餾夢上線、彩排確認品質後就跑大夢；§7 以大夢日為分界分兩段評估。（未採用的 A：排在 2026-11-16 之後，歸因較乾淨，但整庫整理要多等一個月。）

**順序**（每個 agent 各跑一次，兩個 DB 獨立）：

1. **前置**：#616 上線後，lifecycle 先清掉約 1,551 筆沒被用過的舊夢三元組（模擬結果，主 agent）。
2. **收斂**：`convergent_dream(corpus_limit=全庫, max_clusters=全部, max_review_clusters=全部)`，一次把 719 個合併簇（離線重現的數字）消化完。
3. **蒸餾**：`distill_dream(max_neighborhoods=N)` 分批跑，直到沒有符合條件的種子為止。
4. **收尾**：跑 `memory_health(view="corpus")`，對照大夢前的快照。

**彩排先行**：大夢正式執行前，先用唯讀模式跑 20 個鄰域，產出報告給 DK 和絲絲看，確認蒸餾品質後才開執行。這跟收斂夢 P4b 的轉正方式相同。

大夢由 Loom Agent 透過工具在監督下手動執行，不走排程。

## 7. 成功標準與檢查日（DK 握著）

大夢的一次性效果遠大於日常蒸餾的累積效果，混在一起看會無法歸因，所以**以大夢日為分界分兩段**（時程 B）。到期時我（CC）把**原始輸出**交給 DK，不先下結論。

**第一段：大夢本身**（大夢完成後隔天）
1. 大夢前、後的 `memory_health(view="corpus")` 快照對照：總量、非夢記憶量、dup groups。
2. 三組 DK 選的查詢，大夢前、後各跑一次 `recall` 的 top-10 原文。**標準：DK 看得出重複變少、答案變集中。**

**第二段：日常蒸餾夢**（大夢後四週）
3. 每週快照的 Δ7d，分兩條看：**總量**，以及**扣掉夢三元組的非夢記憶量**。**標準：非夢記憶量連續四週 ≤ 0。** 只看總量會把夢三元組 21 天半衰期的自然消失誤算成蒸餾夢的功勞。
4. 以 `metadata.produced_by = "distill_dream"` 篩出蒸餾產物，比較它與其他非夢機器產出記憶的 recall 命中率。**標準：蒸餾產物比較高**（目前基準約 15%）。只算大夢之後產生的蒸餾產物。
5. 兩個 agent 在這四週內有沒有再抱怨重複記憶（DK 觀察）。

**退役判準**：第二段四週後 3–4 都沒有改善 → 蒸餾夢降級回唯讀，回頭檢討（依「四週無行為改變就降級」原則）。

## 8. 實作分階段

| 階段 | 內容 | 驗收 |
|---|---|---|
| P1 | `distill_dream` 唯讀：挑種子 → 收鄰域 → 蒸餾 → 把關 → 報告（寫入 `dreams/`），不改 DB | 契約測試：唯讀不變式、手寫記憶不入 covers 且主張不被複製、夢三元組不當種子 / survivor、diff gate 擋掉資訊遺失、`produced_by` 格式 |
| P2 | `execute=true`：接 `consolidate` + stale check + 備份 | 契約測試：執行後原文可從 metadata 回溯、stub 可 resolve、stale 跳過 |
| P3 | 取代 12 小時主題夢：daemon 的 dream loop 改跑 `distill_dream`；設定 `[memory.distill_dream]`（同步寫進 `loom.toml.example`）。實作：沿用收斂夢的 restart-safe loop（`distill_dream.last_run`），`DreamLoop` 退役；`execute` 同時管 loop 與工具 | daemon 接線測試；03:00 自由夢不受影響 |
| P4 | 大夢彩排（唯讀 20 鄰域）→ DK 看報告 → 正式大夢（兩個 agent） | 第 7 節的大夢前快照已存 |

測試先行（SDD + TDD）：每個階段先寫契約測試（red），再實作。

## 9. 不做什麼

- 不改 03:00 自由夢的產生方式（只受 #616 約束）。
- 不調 admission gate 的 0.85 門檻（見第 10 節）。
- 不做跨 agent 的記憶合併：兩個 DB 各自獨立蒸餾。
- 不引入新的記憶層或 temporal 類別：蒸餾結果就是一般的 semantic fact。

## 10. 待決問題

1. **admission gate 的重複門檻要不要從 0.85 收緊到 0.78？** 釐清機制：這個門檻是**新穎度上限**——候選跟既有記憶的 cos **≥ 門檻**就判成重複、擋下。所以 0.85 → 0.78 是**變嚴格**：會多擋下 0.78–0.85 的「同一件事換個說法」；0.70–0.78 的「同主題不同面向」在兩種設定下都進得來。風險是誤擋真正的新資訊。建議：大夢跑完、日常蒸餾穩定後，用當時重新校準的區間再評估。
2. **`dropped` 的內容要不要另外留一份紀錄給 DK 看**，還是只保存在 survivor 的 metadata 裡？建議只存 metadata，報告裡列出摘要。
3. ~~蒸餾後的記憶 source 要怎麼標？~~ 已定（r2）：`source` 維持原值，另寫 `metadata.produced_by = "distill_dream"`（§4 第 5 步），§7 第 4 點以它篩選。
