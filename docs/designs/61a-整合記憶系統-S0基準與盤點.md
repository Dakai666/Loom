## 1. 結論與需先處理的差異

讓原始經歷可搜尋、再減少自動提煉的方向成立。但 S0 發現三項不能帶著錯誤假設進 S1／S3 的差異：

1. **tool 原始全文並未普遍保存。** 主對話兩條 dispatch 路徑把 `tool_output[:500]` 寫入 session log，沒有傳入 raw JSON。快照中 39,513 筆 tool 列，`raw_json` 非空為 0；content 最長 502 字元。索引或 ref 展開都不能恢復未保存的後段。
2. **subagent 經歷只寫 episodic，沒有寫 session log。** S3 不能直接把 episodic 當成全部冗餘副本刪掉，須先為這個 producer 接上可保存／可查的來源。
3. **trigram 解決子字串索引，不自動解決自然語言改述。** 直接沿用整句 query 的 literal 探針，在 12 個 development log 正例只命中 6 個；改述、跨語言與若干自然問法仍查無。這不是對完整 S1 或模型自主改寫能力的評測，卻足以否定「換 tokenizer 就自然完成語意召回」的推論。

其餘需要修正的盤點：`facade.relate` 沒有經 governor；行為反思與兩條 approval 寫入未被 r1 表格完整區分；legacy supersede 多為原 key 覆寫與 metadata 歷史，沒有另一種可直接扣除的獨立 superseded row flag。

### 2.2 既有 mutation primitives 與維護

| 路徑 | 改什麼 | 不可因 producer 收斂而忽略的邊界 |
|---|---|---|
| `SemanticMemory.upsert`／`ProceduralMemory.upsert` | content／統計／來源／metadata，及 embedding | primitive；呼叫點才是 producer；保留索引 trigger 交易語意 |

## 5. 凍結案例與修改前結果

檔案：`tests/fixtures/memory_s0_cases.json`、`memory_s0_baseline.json`、`memory_s0_embeddings.json.gz`。

- 36 案例：28 正例（24 S1、4 S2），8 無答案／來源不足；development／holdout 在資料中固定。
- 全是合成來源；A–E 使用問法形狀與新的虛構內容，不含 Loom Agent 的私人原文。
- 來源 gold 為 `log:`／`mem:`／`skill:`／S2 `doc:`；每例列 query、原呼叫參數、來源與必須可見片段。多個必要來源另算 all-sources-located。
- 新 ref 只是 metric adapter 的穩定標籤，**不是聲稱舊 runtime 已提供新 identity API**。
- 「沒有 semantic fact」以目標來源未被抽取為準；合成 corpus 仍保留其他干擾 facts／skills，避免只測空資料庫。
- S2 文件原文放在 fixture 中供下一切片接入，不把尚未納入的文件算成 S1 必過來源。
- 調參與品質驗收分 split 計數。holdout 是已凍結、未用來調門檻的集合，不宣稱對維護者隱藏的 blind benchmark；若未來依其失敗調參，需另建 holdout。

| Profile | S1 Hit@5 | 全部正例 Hit@5 | 全來源定位率 | 無答案假命中率 |
|---|---:|---:|---:|---:|
| 無 embedding provider，現行 lexical／fallback | 8/24 | 8/28 | 8/28 | 7/8 |
| 真實本機 Qwen embedding 向量回放 | 8/24 | 8/28 | 8/28 | 7/8 |

這些是本合成集的基準，**不是正式使用成功率**。正例成功來自 mem／skill；log／doc 目標目前無法被 recall 讀取。主分數按「來源正確且顯示片段含必要證據」算，不把相關通則或熟悉文字算成找到經歷。多來源轉折以 all-sources-located 防止只找到其中一方就宣稱完成。

負例的時間限制明確使用 semantic type，避免把既有「skills 不受 semantic 時間軸限制」偷偷改成比較標準；所有新舊條件保存在 baseline。唯一不誤回的負例是 semantic 的空時間窗，其餘 7 個會拿到無關候選／recent fallback。

向量以 production 單筆 query 形狀呼叫本機 `qwen3-embedding:0.6b`，只處理本合成 corpus；40 個輸入、每向量 1,024 維，凍結為 gzip 供離線 replay。fixture hash 與 runtime 檔案 hash 附於基準。向量回放用來固定品質結果，不把其耗時當成網路／模型端到端延遲。

## 6. 副本量測與資料量口徑

原始來源以 SQLite read-only backup 複製；benchmark 驗證 snapshot marker 後再複製一份才做 DDL／recall 存取更新。沒有啟動 Session／daemon／migration CLI，也沒有使用預設 LedgerStore。來源資料庫沒有寫入呼叫；工具只輸出聚合數字。

環境：Python 3.12.11、Python SQLite **3.49.1**，trigram 可用。r1 記錄的 3.52 不能當 Python runtime 版本；以實際執行環境為準。p95 採 nearest-rank。以下時間是在本機、暖機環境的容量基準，不是跨硬體 SLA；逐項數字與完整分位數見相鄰 `61a-memory-s0-metrics.json`。相同 4 query／limit=5／每輪 28 次的兩輪 recall：p50 約 368／350 ms、p95 約 432／360 ms；預算先採較慢一輪，不選較快一輪宣稱改善。量測包括 `MemorySearch.recall` 與結果格式化，不包括完整 agent turn／ledger emit。

### 6.1 排除 stub 後重新計數

| source 分組 | 全部 rows | 非 redirect rows |
|---|---:|---:|
| session | 7,047 | 4,039 |
| dreaming | 1,481 | 888 |
| memorize | 1,119 | 1,087 |
| agent | 221 | 131 |
| task_reflector | 51 | 49 |
| user | 10 | 10 |

redirect stub 3,729。snapshot 的 row／metadata 沒有獨立 superseded 欄位；41 rows 有 `metadata.history`，它們是目前 row 攜帶的舊版本，不是可以再扣掉的 41 個現役 rows。故不捏造第二個「排除 supersede」數字。65.1% 的非 redirect rows 來自 session，與全 rows 約 70.9% 的口徑不同；這不改變停掉例行提煉的產品裁決。

### 6.2 原文與可關聯範圍

- session log 共 85,711 rows：user 7,349、assistant 37,743、tool 39,513、system 1,106。索引 probe 排除 system。
- tool content 長度 p50=323、p95=500、p99=500、max=502；**raw_json 非空 0**。
- tool rows 以 `(session_id, tool_call_id)` 能對到 action_records：37,777/39,513，約 95.6%；其餘須明示缺少關聯，不能靠時間補配。
- action_records 中只有 5,773 筆有新的 output capture；prefix 上限 16,384。其 output_len p50=344、p95=7,420、p99=15,690、max=1,132,470。不能把這個近期待測子集冒充全部歷史 tool 全文。
- 一個 log 回合的 rows p50=7、p95=44、p99=91、max=346；展開「三個回合」本身不是足夠的輸出上限。
- 來源有重複內容 rows；S1 去重時須按回合合併佔位，保留不同回合的轉折，不改寫原始 log。

## 7. S1 上限提案及依據

以下是依量測提出的**初始工程預算**，供 Claude Code review／DK 確認，合併後由 Claude Code 回寫 r2。不是已調得最佳的品質參數，也不是 S0 自行改變 r1 定案。

| 項目 | 提案 | 依據／驗收邊界 |
|---|---|---|
| 每路候選 | 最多 40 個獨立 ref／回合；最終預設 5 筆 | 允許 lexical／vector 互補，同時限制融合與輸出；row 命中先合併再限 ref，不能把 40 個同回合 rows 算成 40 個候選。品質仍以固定案例確認 |
| 一次 ref 展開 | 目標回合＋前後各一，最多 3 回合、總 128 rows、8,000 字元 | 回合 p95=44／p99=91；最大 346，所以必須同時有 row／字元限制並標截斷 |
| 初次輸出 | 5 筆、每筆最多 512 字元，總 4,000 字元含來源／覆蓋 | 舊 limit=5 輸出約千字元；新來源與 ref 留空間，但不把整場 session 塞回。此處是 Unicode 字元，未冒充 tokenizer token 數 |
| 現有 tool 的索引前段 | **512 字元** | 目前 content max=502；512 已保留全部「實際保存的摘要」，4,096／16,384 對舊資料沒有新增內容 |
| 若新增完整 tool 保存 | **8,192 索引字元供另行核定** | 新 action capture 子集有 96.3% 的原輸出長度不超過 8,192；完整 ref 仍須讀實際 source。此項會擴大 r1 source 保存範圍，成本需重新量，不冒充已驗證 |
| 兩字詞掃描 | 最多 100,000 rows／150 ms，最多回 40 個 ref | 本快照 85,711 rows，無命中最慢約 92 ms；現有常見詞提早滿額很快，不能只量常見詞。超限須明示只查到哪一段／來源部分覆蓋，不能回「不存在」 |
| recall 暖機 p95 | **700 ms**，以相同 query／limit／provider 比較 | 舊路徑約 432 ms；留給新增 lexical／短詞掃描與受限展開約 268 ms。完整 agent 改寫迴圈另計，不把 backend 預算當端到端回答延遲 |
| 既有 content 的 migration | 新索引頁淨增 ≤128 MiB，單機 rebuild ≤30 s | log trigram 約 74 MiB；semantic trigram 約 8.2 MiB、舊約 1.8 MiB；實測合計約 9 s。僅適用目前 content；新增 raw 全文後需重估 |
| 額外必跑 LLM | 0 | 維持 r1；索引／展開／融合均不需要隱藏模型鏈。主模型自主追查的成本另記 |

若只想先交付「工具摘要可搜」，512 合理，但必須把結果標成摘要。若要承諾新增經歷的工具原文可回找，須調整保存點；不能只把 prefix 改大。

## 8. 必須在 r2 說清楚的三個問題

1. **工具回覆的權威來源。** 建議承認舊 tool 摘要的有界保存；對新資料是否把完整 tool message 存入既有 raw_json，連同 read-time redaction、超長內容與容量一併定案。S0 沒有實作這個範圍擴充。關閉 compress 的驗收不能聲稱能恢復原本沒存的全文。
2. **改述／跨語言的驗收層級。** `probe` 只測 development，literal trigram/LIKE 找到 6/12 個 log 正例，其餘包含無連續字面重疊的問法。請明訂 S1 是單次工具 query 必須命中，還是允許主模型以相同使用者問題自主改寫搜尋詞再追查；後者不能偷換成同條件的 single-call 改善。若保留單次直查要求，需另提能通過的方案及成本；不默默加 session embeddings 或 hidden LLM router。
3. **child 經歷的替代與 episodic 退役。** S1 主對話先完成不受影響；S3 停 child episodic 前，先接來源與測一次「child 工具失敗→原始經歷可讀」。不將其當作已在 session log 的第三份副本。

另有一項實作要求：external-content FTS 若只索引 tool 前段，`rebuild`、insert、update、delete 必須使用**相同內容投影**。不能 trigger 插入截斷文字、external content 卻指向全文，否則 delete／integrity 不一致。S0 probe 用同一 computed view＋同一 CASE 表達式，合成測試涵蓋 update、role 改變、delete、rebuild 與 integrity-check；這是量測用 DDL，不是替 S1 決定 migration。

## 9. 重現方式、檔案與驗證

公開離線品質 replay：

```sh
python scripts/memory_s0.py synthetic --replay tests/fixtures/memory_s0_embeddings.json.gz --output /tmp/memory-s0-replay.json
python scripts/memory_s0.py probe --output /tmp/memory-s0-literal.json
python -m pytest tests/test_memory_s0.py tests/test_memory_search.py tests/test_memory_period_recall.py tests/test_memory_facade.py -q
```

副本量測使用明確的來源／目的路徑：先執行 `snapshot --source <source.db> --destination <new-copy.db>`，再執行 `benchmark --snapshot <new-copy.db> --output <aggregate.json> --ollama-url http://localhost:11434 --repeats 31`。source 以 `mode=ro`／query_only 開啟；destination 必須全新。benchmark 再複製，不對 snapshot 原件做 DDL。JSON 輸出拒絕覆寫資料庫或指向 live state 的別名。

`scripts/` 在 repo 原本被忽略，本 PR 只明確納入新的 `memory_s0.py`，不把其他工作區操作腳本帶入。private DB／marker／向量生成中間檔不進 git；只有合成向量與聚合報告可公開。

S0 驗證涵蓋 gold 可定位／片段存在、holdout、rank 截斷、多來源轉折、負例、snapshot 不改來源與拒絕覆寫、trigram 兩字限制、外部內容索引一致性、離線向量 replay。凍結 baseline 不設成未來 runtime 必須維持低命中率的斷言；S1 改善時保留這份修改前證據。
